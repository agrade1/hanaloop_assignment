# 구현 방향 및 의사결정 기록

이 문서는 PCF 전과정 데이터 시각화 대시보드 과제를 진행하면서 내린 주요 구현 방향과 의사결정을 기록하기 위한 문서이다.

과제에서 TypeScript와 Next.js 사용이 명시되어 있으므로, 본 문서에서는 해당 기술을 선택한 이유보다 주어진 기술 요구사항을 어떤 방식으로 활용할지와 구현 범위를 어떻게 정했는지를 기록한다.

## 1. Next.js 사용 방향

과제 요구사항에 Next.js가 명시되어 있으므로, 프로젝트는 Next.js 기반으로 구성한다.

초기 구현에서는 복잡한 서버 기능보다 PCF 계산 흐름과 대시보드 시각화가 핵심이라고 판단했다.

따라서 Next.js는 다음 목적에 집중하여 사용한다.

- App Router 기반의 명확한 프로젝트 구조 구성
- 대시보드 페이지 단위 관리
- React 컴포넌트 기반 UI 분리
- 향후 API 또는 DB 연동으로 확장 가능한 구조 확보
- Vercel 배포 가능성 확보

초기 구현은 단일 대시보드 화면을 중심으로 구성하되, 기능 단위 폴더를 분리하여 추후 제품 상세 페이지나 리포트 페이지로 확장할 수 있도록 한다.

## 2. TypeScript 사용 방향

과제 요구사항에 TypeScript가 명시되어 있으므로, 주요 데이터 구조와 계산 로직은 TypeScript 타입을 기반으로 작성한다.

PCF 대시보드는 제품, 생애주기 단계, 활동량, 배출계수, 계산된 배출량 등 도메인 데이터의 구조가 중요하다.

따라서 TypeScript를 단순한 문법 체크 용도가 아니라, 데이터 흐름을 명확히 표현하는 도구로 사용한다.

초기에는 다음과 같은 타입을 정의할 예정이다.

- Product
- LifecycleStage
- ActivityRecord
- CalculatedEmission
- ProductEmissionSummary

실제 타입 구조는 과제용 데이터 확인 후 조정한다.

## 3. Postgres를 초기 구현에서 제외하는 이유

과제에서 Postgres는 Optional로 명시되어 있다.

이번 과제의 핵심은 데이터 저장소 구축보다, 과제용 데이터를 기반으로 PCF 계산 흐름을 이해하고 이를 대시보드로 시각화하는 것이라고 판단했다.

따라서 초기 구현에서는 Postgres를 사용하지 않고, 정적 JSON 또는 TypeScript 데이터 파일을 기반으로 기능을 구현한다.

초기 범위에서 Postgres를 제외한 이유는 다음과 같다.

- 제한된 시간 안에 핵심 기능인 계산 로직과 시각화 완성도를 높이기 위해
- 데이터베이스 설정보다 프론트엔드 대시보드 구현에 집중하기 위해
- 과제용 데이터가 정적 데이터라면 DB 없이도 계산 흐름을 검증할 수 있기 때문에
- 향후 API 또는 DB 연동이 가능하도록 데이터 접근 계층을 분리할 수 있기 때문에

단, 데이터 구조는 향후 Postgres 또는 외부 API로 교체할 수 있도록 UI와 계산 로직에서 직접 의존하지 않게 설계한다.

## 4. PCF 계산 로직과 UI를 분리하는 이유

PCF 계산 로직은 UI 컴포넌트 내부에 직접 작성하지 않는다.

계산 로직을 UI와 분리하는 이유는 다음과 같다.

- 계산 기준 변경 시 수정 범위를 줄일 수 있다.
- 차트, 요약 카드, 테이블에서 동일한 계산 결과를 재사용할 수 있다.
- UI 컴포넌트는 표시 역할에 집중할 수 있다.
- 계산 로직을 별도로 검증하기 쉽다.
- 향후 API 또는 DB 연동 시에도 계산 모듈을 재사용할 수 있다.

## 5. 데이터 입력 화면 및 검증 정책

본 과제의 데이터 입력 UI는 다음 두 가지로 한정한다. 자세한 범위는 `ASSIGNMENT_BRIEF.md`의 "데이터 입력 UI 범위" 절을 따른다.

1. 엑셀 업로드 화면
2. 감축 시나리오 입력 화면

### 5.1 엑셀 업로드 검증

업로드된 파일에 대해 다음 검증을 수행하고, 실패 시 에러 메시지를 화면에 표시한다.

- 파일 확장자가 `.xlsx`인지 확인한다.
- 필수 컬럼(예: 제품명, 생애주기 단계, 활동량, 단위, 배출계수)이 모두 존재하는지 확인한다.
- 활동량과 배출계수가 숫자이며 음수가 아닌지 확인한다.
- 단위가 사전에 정의된 단위 목록에 포함되는지 확인한다.
- 제품·단계 조합 내 중복 레코드 존재 여부를 확인한다.

에러 메시지는 어떤 행/컬럼에서 어떤 이유로 실패했는지 사용자가 파악할 수 있도록 구체적으로 표시한다.

### 5.2 감축 시나리오 입력 검증

- 감축률은 0~100% 사이의 숫자여야 한다.
- 빈 값, 문자열, 음수, 100 초과 값은 에러 메시지로 안내한다.
- 시나리오 적용 결과는 원본 데이터를 변경하지 않고 별도 계산 결과로 표시한다.

### 5.3 향후 확장: 활동 데이터 CRUD

MVP 이후 시간이 남는 경우, 활동 데이터를 UI에서 직접 추가/편집할 수 있는 화면을 추가한다. 이때 필수 필드/단위/형식 검증은 위의 엑셀 업로드와 동일한 기준을 적용한다.

## 6. 단위 표시 정책

PCF 데이터는 단위 표기가 정확해야 의미가 전달되므로 다음 정책을 적용한다.

- 기본 단위는 `kgCO₂e`로 통일하여 계산하고 표시한다.
- 값이 큰 경우(예: 1,000 kgCO₂e 이상) 자동으로 `tCO₂e` 단위로 변환하여 표기한다.
- 활동량 단위(kg, kWh, km 등)는 입력 데이터의 단위를 유지하여 표 형태로 표시한다.
- 차트 축, 카드, 테이블의 단위는 명시적으로 표기하며, 단위 없는 숫자는 표시하지 않는다.
- 천 단위 구분자와 소수점 표기는 일관된 포맷터(`Intl.NumberFormat`)를 통해 처리한다.

## 7. 패키지 매니저: yarn 고정

과제 평가 기준에 `yarn start`로 실행 여부가 포함되어 있으므로, 본 프로젝트는 yarn을 패키지 매니저로 고정한다.

- 의존성 관리와 스크립트 실행 모두 yarn을 사용한다.
- `package.json`의 `scripts.start` 명령은 Next.js 표준 실행 명령을 그대로 사용한다.
- npm 또는 pnpm 사용을 막기 위해 `packageManager` 필드를 명시한다.

## 8. 데이터 접근 계층 추상화 방식

향후 정적 JSON에서 Postgres 또는 외부 API로 데이터 소스를 교체할 수 있도록, UI/계산 로직은 데이터 소스에 직접 의존하지 않는다.

다음과 같은 인터페이스 계층을 둔다.

- `DataSource` 인터페이스: `getProducts()`, `getActivities()`, `getEmissionFactors()` 등 도메인 메서드를 정의한다.
- 초기 구현은 정적 JSON 또는 빌드 타임에 임포트된 데이터를 사용하는 `StaticDataSource`로 한다.
- 향후 Postgres 도입 시 동일한 인터페이스를 구현하는 `PostgresDataSource`를 추가하여 교체 가능하게 한다.

UI 컴포넌트는 `DataSource` 인터페이스를 통해서만 데이터에 접근하며, 데이터 소스 구체 구현체에 직접 의존하지 않는다.

## 9. Trade-off 정리

본 과제에서 의식적으로 선택한 trade-off는 다음과 같다.

### 9.1 정적 JSON vs Postgres

- **선택**: 초기 구현은 정적 JSON 기반으로 진행한다.
- **포기한 것**: 실시간 데이터 갱신, 다중 사용자 데이터 분리, 영속화.
- **얻은 것**: 빠른 MVP 완성, 의존성 단순화, `yarn start`만으로 즉시 실행 가능한 구조.

### 9.2 풀 CRUD vs 업로드 + 시나리오 입력

- **선택**: 엑셀 업로드와 감축 시나리오 입력만 제공한다.
- **포기한 것**: 활동 데이터를 UI에서 직접 추가/편집하는 흐름.
- **얻은 것**: 핵심인 계산 흐름과 시각화에 집중할 수 있는 구현 범위.

### 9.3 차트 라이브러리 사용 vs 직접 구현

- **선택**: 검증된 차트 라이브러리(예: Recharts)를 사용한다.
- **포기한 것**: 시각적 디테일에 대한 완전한 제어.
- **얻은 것**: 짧은 시간 안에 일관된 차트 품질 확보.

## 10. Postgres 도입 시점 재검토

3장에서 설명한 대로 MVP에서는 Postgres를 사용하지 않는다. 단, 과제 보너스 항목 중 "과제용 엑셀 데이터를 별도 가공 없이 PostgreSQL에 임포트할 수 있는 인터페이스"에 대한 가점이 존재한다.

따라서 MVP 완성 후 시간이 남는 경우, 다음 순서로 보너스 작업을 추가한다.

1. Docker Compose를 통한 Postgres 컨테이너 구성
2. 엑셀 파일을 그대로 임포트할 수 있는 API 엔드포인트 구현
3. 동일 인터페이스를 만족하는 `PostgresDataSource` 구현체 추가
4. README 실행 방법에 `docker compose up` 단계 추가

이 작업은 MVP 필수·권장 항목을 모두 충족한 뒤에 진행한다.
